# Interview Agent AI Coding 工程实践总结

**版本：V1.0**  
**状态：[持续维护]**  
**适用阶段：Phase 3 及后续开发**

## 文档目的

本文总结 Interview Agent 从需求分析、架构设计到 Slice / Task 迭代过程中形成的 AI Coding 工程实践。

这些结论来自实际开发中的成功经验与返工教训，主要用于：

- 约束 ChatGPT 与 Codex CLI 的协作方式；
- 控制 Slice 和 Task 的范围；
- 降低一次性大任务造成的返工风险；
- 指导技术债与非主线问题的处理；
- 持续沉淀可用于项目复盘和面试表达的方法论。

本文不是具体功能或架构的 Source of Truth。业务与技术设计仍以对应需求文档、架构文档、ADR 和当前 Slice 设计为准。

## 核心结论

Interview Agent 当前验证出的开发方式可以概括为：

> **先由人确定目标、边界和关键决策，再由 AI 完成小而完整的实现闭环，最后由人负责验收、取舍和推进节奏。**

当 Slice 方向正确、Task 拆分合理、Spec 足够清晰时，Codex CLI 可以高质量完成绝大部分甚至全部代码编写，包括实现、测试和必要文档更新。

这并不意味着工程师只需要提出一句模糊需求。人的主要职责正在从“亲手编写每一行代码”转向：

- 判断需求是否值得做；
- 确定当前阶段做到什么程度；
- 划分 Slice 与 Task 边界；
- 识别高成本设计决策；
- 在多个可行方案中进行取舍；
- 控制 AI 的修改范围；
- Review、验收并决定何时停止；
- 管理技术债与长期文档一致性。

## 已验证有效的实践

### 方向正确和任务拆分决定 AI 的交付质量

Codex CLI 的表现高度依赖输入任务的质量。

如果一个 Task 同时包含多个业务目标、模糊边界和未确认设计，AI 即使能生成大量代码，也容易出现：

- 自行补充设计；
- 修改范围扩大；
- 前后假设不一致；
- 测试只能覆盖局部；
- Review 困难；
- 返工牵连多个模块。

更有效的前提是：

- Slice 的业务目标和主流程已经明确；
- 跨 Task 的关键边界已经确认；
- 当前 Task 只包含一个可验证的业务能力；
- 输入、输出、状态变化、异常和验收标准清楚；
- 明确列出不属于当前 Task 的内容。

### 采用“两级设计 + 小步实现”

不应在两个极端之间选择：

- 完全不做整体设计，直接逐个 Task 开发；
- 把整个 Slice 的所有细节一次性设计完成，再交给 AI 批量实现。

更合适的方式是：

#### Slice 级设计

设计到足以保证方向正确，重点确认：

- 目标与范围；
- 主流程；
- 模块职责；
- Task 拆分；
- Task 之间的输入输出；
- 状态、事务、持久化和 LLM 调用边界；
- 会影响多个 Task 的关键决策。

Slice 级设计不追求提前确定所有类、方法和字段。

#### Task 级设计

当前 Task 开始前再详细确认：

- 业务输入与输出；
- 领域对象和接口；
- 状态变化；
- 异常与失败处理；
- LLM 行为和 Prompt 要求；
- 测试场景；
- Out of Scope；
- 验收标准。

确认后立即实现、测试和 Review，通过真实代码反馈修正下一步设计。

### Task 必须按业务能力拆分

Task 不应按代码分层或文件类型拆分。

不推荐：

~~~text
Task 1：创建 DTO
Task 2：创建 Service
Task 3：创建 Repository
Task 4：补测试
~~~

推荐：

~~~text
Task：实现 Question Generation 能力，
包含必要领域模型、应用服务、AI Adapter 和测试。
~~~

一个合格的 Task 应满足：

- 只有一个主要业务目标；
- 完成后系统增加一个可验证能力；
- 包含实现该能力所需的最小纵向链路；
- 能独立测试和 Review；
- 失败或返工不会大范围影响其他 Task。

### 文档必须随项目持续维护

随着项目持续迭代，代码、设计和项目上下文会不断变化。文档如果只在项目开始时创建，后续很快会与真实实现脱节。

文档维护的重点不是增加 Markdown 数量，而是保证关键事实可被重新获取：

- 当前业务规则；
- 已确认的架构决策；
- Slice / Task 进度；
- 状态与生命周期；
- 延后的技术债；
- 实现中暴露出的设计偏差；
- AI Coding 的实践规则和复盘结论。

文档更新应遵循“最小必要同步”：

1. 更新实际受影响的 Source of Truth；
2. 重大且长期有效的决策写入 ADR；
3. Phase / Slice 状态和验收结果更新到 Progress；
4. 只有项目导航信息变化时才更新 PROJECT_CONTEXT；
5. 过程经验写入 Retrospective；
6. 不在多个文档中重复维护同一份完整定义。

## 最重要的范围控制规则

### 不让非主线问题扩展当前 Task

Task 实现过程中经常会发现相邻问题，例如：

- 旧代码命名不统一；
- 某个类还可以继续拆分；
- 存在未来扩展点；
- 某些索引可以优化；
- 局部代码风格可以统一；
- 另一个模块也存在相似问题。

发现问题不等于必须在当前 Task 解决。

先判断：

1. 是否阻塞当前 Task 的实现或验收？
2. 不处理是否会导致错误数据、严重回归或高成本返工？
3. 是否属于本 Task 已确认的业务目标？
4. 修改是否会扩大到其他模块或引入新设计？

如果问题不影响主线，应记录后继续当前 Task。

### 小问题优先记录为技术债

技术债不是忽略问题，而是有意识地选择处理时机。

适合延期的问题通常具备以下特征：

- 不影响当前功能正确性；
- 不阻塞后续核心 Slice；
- 后续可以局部重构；
- 缺少真实运行数据，当前难以确定最优方案；
- 收益小于打断主线造成的成本。

每条技术债至少记录：

- 问题是什么；
- 当前为什么不处理；
- 可能造成什么影响；
- 建议在什么条件或阶段处理。

以下情况不能简单延期：

- 数据正确性或一致性风险；
- 安全问题；
- 会污染已持久化业务历史的问题；
- 明显阻塞下一个 Task 的设计缺陷；
- 修复成本会随迭代快速上升的问题。

### 每个 Task 固定声明 Out of Scope 和 Tech Debt

后续 Task Spec 建议固定包含：

#### Out of Scope

明确当前 Task 不处理的内容，用于约束 AI 不进行顺手重构或未来能力建设。

#### Tech Debt

记录执行过程中发现但不阻塞当前 Task 的问题。本 Task 只记录，不扩大实现范围。

## 常见失控模式

典型的失控路径是：

~~~text
发现问题 A
→ 顺手处理相邻问题 B
→ B 引出设计问题 C
→ C 需要重构组件 D
→ Task 修改范围扩大
→ 上下文和测试复杂度上升
→ 出现回归
→ 继续追加修复
~~~

当出现以下信号时，应立即检查 Task 是否失焦：

- Task 的主要目标已经无法用一句话描述；
- 新增工作与原验收标准无关；
- 修改开始跨越多个无关模块；
- AI 被要求同时设计并实现后续 Task；
- Review 中大部分问题来自顺手重构；
- 同一个 Task 多次出现“大范围修复”；
- 讨论持续扩展，但核心业务能力仍未完成。

处理方式：

1. 回到当前 Task 的目标和验收标准；
2. 保留阻塞主线的问题；
3. 将其余问题转入 Tech Debt；
4. 必要时将新增业务能力拆成独立 Task；
5. 当前 Task 闭环后再决定是否处理。

## AI 方案的选择原则

AI 容易给出完整、通用、可扩展且形式漂亮的方案。这些方案可能在理论上成立，但不一定适合当前 MVP。

工程师需要判断的不是“方案是否足够完整”，而是：

- 是否解决当前真实问题；
- 是否匹配当前阶段；
- 是否已有第二个真实实现或变化点；
- 是否能被当前测试和运行数据验证；
- 新增复杂度是否值得；
- 未来扩展是否真实存在；
- 如果未来需要，届时重构成本是否可以接受。

例如，一个简单方案可以满足当前 95% 的确定需求，而复杂方案只是为了尚未发生的扩展提供能力，MVP 阶段通常应选择简单方案。

只有满足以下条件之一时，才优先增加抽象或通用机制：

- 已存在两个真实实现；
- 变化点已经在代码中出现；
- 可以消除真实重复；
- 测试替换确实需要边界；
- 不提前处理会造成明确且高成本的返工。

> **AI 提供的是候选方案，工程师负责选择当前约束下最合适的方案。**

## ChatGPT 与 Codex CLI 的建议分工

### ChatGPT / Work 模式

主要负责：

- 需求澄清；
- Slice 方向与边界；
- 关键方案讨论；
- Task 拆分；
- Spec 编写；
- 方案取舍；
- Code Review；
- 项目复盘和文档沉淀。

### Codex CLI

主要负责：

- 读取仓库当前代码与约束；
- 按已确认 Spec 实现代码；
- 编写和执行测试；
- 完成局部、明确的重构；
- 修复 Review 中确认的问题；
- 输出实际改动和验证结果。

### 开发者

始终负责：

- 确认最终目标；
- 选择方案；
- 决定范围；
- 验证业务语义；
- Review 关键代码和测试；
- 判断技术债是否可接受；
- 决定是否合并和何时进入下一 Task。

## 推荐的标准开发流程

~~~text
Slice 目标与范围
→ Slice 主流程与跨 Task 决策
→ 按业务能力拆分 Task
→ 当前 Task 详细设计
→ 编写小而完整的 Codex Spec
→ Codex 实现与测试
→ 本地验证与人工检查
→ Code Review
→ 当前 Task 内修复阻塞问题
→ 记录非阻塞技术债
→ 合并
→ 进入下一 Task
~~~

### Slice 开始前

- [ ] 目标、非目标和验收结果是否清楚？
- [ ] 主流程是否已经确定？
- [ ] Task 是否按可验证业务能力拆分？
- [ ] 跨 Task 的状态、事务和接口边界是否明确？
- [ ] 是否避免提前设计全部实现细节？

### Task 开始前

- [ ] 主要目标是否可以用一句话描述？
- [ ] 输入、输出和状态变化是否明确？
- [ ] 异常和失败行为是否明确？
- [ ] 是否列出 Out of Scope？
- [ ] 验收标准是否可执行？
- [ ] 是否包含必要测试？
- [ ] 修改范围是否足够小，可以独立 Review？

### Task 执行中

- [ ] 新发现的问题是否阻塞主线？
- [ ] 是否出现与验收标准无关的修改？
- [ ] 是否把低优先级问题记录为技术债？
- [ ] AI 是否开始自行扩展需求或设计？
- [ ] 当前实现是否仍是最小可运行方案？

### Task 完成前

- [ ] 核心能力是否形成可运行闭环？
- [ ] 编译和关键测试是否通过？
- [ ] 是否人工检查了业务语义？
- [ ] Review 问题是否已处理或明确延期？
- [ ] 必要文档是否同步？
- [ ] Git 提交是否只包含当前 Task 的相关改动？

## 当前项目经验的客观定位

Interview Agent 目前已经形成两类不同的项目价值。

### 已经形成的价值：AI-assisted Software Engineering

当前最成熟的经验是：

- 从零进行需求分析和架构设计；
- 使用 Slice / Task 管理复杂度；
- 通过 Spec 驱动 AI 编码；
- 让 AI 完成代码和测试；
- 通过 Review 和验收控制质量；
- 管理文档、上下文和技术债；
- 识别 AI 过度设计及任务失控问题。

这已经是一套真实的 AI Coding 工程实践，而不只是“让 AI 生成几段代码”。

### 仍需继续加强的价值：AI-native Application Engineering

截至当前阶段，项目中的 AI / Agent 深度仍有限。项目主要证明了“如何使用 AI 开发工程化系统”，还需要后续功能进一步证明“如何开发 AI-native 系统”。

后续可以通过真实业务需求逐步积累：

- Resume / Project / Interview Context Engineering；
- 动态问题生成；
- 回答评价；
- 追问与下一步决策；
- Structured Output 稳定性；
- Prompt 版本与效果评估；
- 长短期记忆；
- RAG；
- Tool Calling；
- Graph / Agent Workflow；
- AI 可观测性与失败恢复。

这些能力应由实际 Slice 驱动，不为了让项目显得更“Agent”而一次性堆入 MVP。

## 面试表达建议

不应只描述为：

> “项目代码 100% 由 AI 编写。”

更准确的表达是：

> **我通过需求澄清、Slice 设计、Task 拆分和 Spec 驱动，让 AI 承担代码与测试实现；我负责关键工程决策、范围控制、Code Review、验收和技术债管理。项目实践让我认识到，AI Coding 的关键不只是生成代码，而是给 AI 建立清晰边界，并在复杂度、扩展性和交付速度之间做出工程取舍。**

这个表述既能体现 AI 使用深度，也不会弱化个人在项目中的核心贡献。

## 后续持续维护原则

本文应在出现以下情况时更新：

- 某种 Task 拆分方式被反复证明有效或无效；
- Codex CLI 出现新的典型失控模式；
- 项目形成新的 Review、测试或文档协作方法；
- 技术债管理规则需要调整；
- 项目开始积累真实 AI / Agent 工程经验；
- MVP 完成并进行阶段性总复盘。

每次更新优先增加可复用的规则、实际现象和判断标准，避免加入只有口号、无法指导下一次开发的内容。

## 最核心的实践原则

> **先确定正确方向，再拆分小而完整的业务任务。**

> **AI 可以完成代码实现，但人必须负责做什么、不做什么、做到什么程度以及何时停止。**

> **不影响主线的问题先记录，不让局部优化拖垮核心交付。**

> **文档记录关键事实和决策，不以文档数量代替可运行成果。**

> **先完成可用的 MVP，再由真实反馈决定哪些复杂能力值得建设。**
